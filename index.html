v0.6.0 beta Behaviour-driven development for Rust

BDD that runs as cargo test.

rstest-bdd binds Gherkin scenarios to plain rstest tests. One runner, shared fixtures, no bespoke world object. Write the feature file; the compiler checks the steps.

Why rstest-bdd

Most BDD frameworks arrive with a runner, a world object, and opinions about both. rstest-bdd arrives with an attribute macro.

One runner. The one already installed.

Scenarios execute as ordinary cargo test tests. Filters, parallelism, IDE integration, and CI pipelines carry on unchanged, because nothing about the toolchain changed.

First-class fixtures

Unit, integration, and BDD tests share the same rstest fixture graph. State lives where rstest puts it – not in a framework-mandated World struct.

Missing steps fail the build

Steps register at compile time. A scenario step with no matching implementation is a compile error with a span, not a surprise at minute forty of the CI run.

Typed placeholders

Patterns such as {count:u32} parse arguments via FromStr before the step body runs. Regex groups remain available for the rare case that needs them.

Quick start

A feature file names the behaviour. Plain functions implement the steps. An attribute binds the two together.

Run it with cargo test. Under the rind, #[scenario] expands to an rstest test, so each scenario – and each Scenario Outline case – appears individually in the test runner. The &mut Basket borrows are new in v0.6.0: mutable access to by-value fixtures, no RefCell ceremony.

New in v0.6.0

The landmark change: scenario execution is now harness-driven. Async runtimes, windowing frameworks, and custom infrastructure plug in through one adapter interface instead of framework-specific flags.

Harness adapters

#[scenario] and scenarios! accept a harness = ... argument. Three first-party harnesses ship ready to use – StdHarness, TokioHarness, and GpuiHarness – and each infers its matching attribute policy. Custom harnesses implement one trait in rstest-bdd-harness. 

#[scenario(path = "tests/features/search.feature",
           harness = rstest_bdd_harness_tokio::TokioHarness)]
fn search_works(world: SearchWorld) {}

HarnessAdapter::run returns HarnessResult<T>, so a Tokio runtime that fails to build surfaces as HarnessError::RuntimeBuildFailed – an infrastructure failure, kept distinct from a scenario assertion failure.

Mutable fixtures, minus the ceremony

Steps can request &mut Fixture when the fixture is provided by value. Modelling a mutable world no longer requires Cell or RefCell wrappers.

Structured execution errors

The new ExecutionError enum replaces string-encoded skip messages with proper variants: Skip, StepNotFound, MissingFixtures, and HandlerFailed.

Skip-aware assertions

assert_step_ok!, assert_step_err!, assert_step_skipped!, and assert_scenario_skipped! assert step outcomes without manual pattern matching.

Typed data tables

Gherkin tables parse into datatable::Rows<T> for row-typed access, or stay as Vec<Vec<String>> where that suffices.

Language server controls

The language server accepts --workspace-root and --debounce-ms, so editor integrations can pin workspace discovery and tune file-change processing.

Predictable fixture names

Implicit fixture names now normalize exactly one leading underscore: _world and world resolve to the same fixture. Explicit #[from(...)] names remain exact.

Migrating from v0.5.x

Three breaking changes, all mechanical: underscore normalization, the deprecated runtime = "tokio-current-thread" alias, and the HarnessResult return type on custom adapters. The migration guide covers each with before-and-after code.

A different trade-off, not a replacement

cucumber-rs ports classic Cucumber to Rust and does it well. rstest-bdd offers BDD as an extension of rstest for teams already invested in cargo test. Step macros accept cucumber's expr = "..." syntax to ease migration.

Feature files in any Gherkin language

Declare a locale on the first line of the feature file and the parser loads the matching keyword catalogue – no configuration. Runtime diagnostics ship as Fluent translations with English fallback, and the japanese-ledger example runs two Japanese scenarios end to end under cargo test. 

# language: fr
Fonctionnalité: Panier
  Scénario: Ajouter un article
    Étant donné un panier vide
    Quand l'utilisateur ajoute une citrouille
    Alors le panier contient une citrouille

Grow the suite on the trellis already standing
